# HyperVault 화면 (2026-10-12)

새 공개 화면은 영어다. 기존 한국어 패널은 그대로 둔다.

| 주소 | 화면 |
| --- | --- |
| `#/` | 홈: 소개, 세 Vault 비교표, HyperEVM↔HyperCore 구조, 신뢰 경계, 증거·모니터 요약 |
| `#/vaults` | HYPE / BTC(UBTC) / USDC 카드. `VITE_DIRECT_VAULTS`에 없으면 "Not deployed — local implementation only" |
| `#/vaults/<주소>` | 매니페스트 Vault 상세: 기준 자산 NAV·지분 가격·EVM 현금·Core 토큰/lending/perp 계정가치(precompile), NAV 차단 사유, 관측 블록·시각, strategy.json의 원노출/추가 헤지 분리, 내 지분·출금 요청·청구 가능액, 잘못된 네트워크 전환, 기존 입출금 패널(`Assets`) |
| `#/vaults/<주소>/trade` | 매니페스트 Vault의 owner 거래 패널(`panels/Trade.tsx` 재사용). 주문 결과를 대기/체결/부분 체결/미체결/거부로 구분 |
| `#/ops` | 역할, 매니페스트 Vault의 대기 액션·배정 큐·epoch, `monitor.json` 규칙표·30분 경과 경고·AI 요약(권한 없음 표시) |
| `#/strategy` | `pm-comparison.json`(가정 → 비교표), `strategy.json`(dry-run/executed 구분) |
| `#/assets` | 기존 자산별 입출금·운용자 콘솔 |
| `#/explore`, `#/create`, `#/vault/...` | `VITE_LEGACY_FACTORY_UI=true`일 때만. 데모 데이터에는 "DEMO DATA" 배너 |

- 읽을 수 없는 값은 0이 아니라 "not observable"로 표시한다.
- JSON은 실행 중 같은 출처에서 읽는다(CSP `connect-src`에 `'self'` 추가). 없거나 비면 "not published", 형식 오류는 오류 상태로 표시하고 아무 값도 그리지 않는다. `"example": true`이면 EXAMPLE DATA 배너. 형식 예시는 `public/hypervault/*.example.json`이며 실제 파일은 다른 스크립트가 쓴다. 검증기는 `src/hypervault.ts`, 테스트는 `src/hypervault.test.ts`.
- 새 환경 변수: `VITE_REPO_URL`, `VITE_VIDEO_URL`(https만, 비우면 링크 숨김). 매니페스트 항목에 선택 필드 `kind`(`HYPE`/`UBTC`/`USDC`)를 둘 수 있고, 없으면 이름으로 판별한다. 상세 화면은 bridge의 `kind`를 우선한다.
- 데모 모드 전환 버튼은 legacy 화면이 켜진 빌드에서만 보인다.

## 메인넷 설정과 배포 (vault.hypurrquant.com)

`.env.production`이 빌드 설정이다(커밋됨, 공개 값만). chain 999, 배포된 USDC Vault 1개의 매니페스트(`kind: "USDC"`), `VITE_ENABLE_WRITES=true`(방문자가 자기 지갑으로 입금·출금 요청·청구), `VITE_ENABLE_TRADING=false`. HYPE·UBTC Vault는 배포되지 않았으므로 매니페스트에 없다. `.env.local`이 있으면 그 값이 우선하니 배포 빌드 전에 확인한다.

Vercel 준비만 되어 있고 배포는 실행하지 않았다.

- 프로젝트 Root Directory: `frontend`
- `vercel.json`: install `npm ci --ignore-scripts`, build `npm run build && node --experimental-strip-types scripts/check-policy.mjs`, output `dist`. 해시 라우팅이라 rewrite가 필요 없다.
- 헤더: CSP는 빌드된 페이지의 meta 태그가 담고, meta로 줄 수 없는 `frame-ancestors 'none'`과 `X-Frame-Options`, `nosniff`, `Referrer-Policy`, HSTS를 `vercel.json`이 보낸다. `hypervault/*.json`은 `no-cache`.
- 환경 변수: 별도 설정 불필요(`.env.production`). Vercel 대시보드에 같은 이름을 넣으면 그 값이 빌드에 들어가므로 넣지 않는다. 비밀 값은 없다.
- Node 22.12 이상(Project Settings → Node.js Version 22.x).
- 도메인: Project → Domains에 `vault.hypurrquant.com` 추가 후 DNS에 `CNAME vault → cname.vercel-dns.com`.
- 증거·모니터 JSON(`public/hypervault/*.json`)은 스크립트가 갱신하므로 갱신 후 다시 빌드·배포해야 반영된다.

# 현재 기본 경로: 직접 배포 Vault

`#/`와 `#/assets`는 플랫폼의 직접 배포 Vault를 표시한다. 공개 생성 기능은 기본으로 노출하지 않는다. `VITE_DIRECT_VAULTS` JSON 배열에 검증된 name/vault/asset/bridge/verifier/controller/implementation/router를 넣는다. 실제 배포 전에는 `[]`로 유지한다. [필드·배포 절차](../docs/direct-vaults.ko.md).

`VITE_ASSET_FACTORY_ADDRESS`는 새 기본 화면에서 사용하지 않는다. 이전 Factory 화면은 `VITE_LEGACY_FACTORY_UI=true`로 명시적으로 켜는 이력 기능이다. 아래 설명 중 Factory 관련 내용은 이전 경로다.

# Managed USDC Vault FE

React / TypeScript / Vite / viem으로 만든 화면이다. 볼트를 만들고, 다른 사람이 만든 볼트를 살펴보고, 볼트 운용자가 HyperCore에 주문을 내고, 운용자와 예치자가 대화한다.

처음 열면 **가상 데이터 데모**가 보인다. 데모는 지갑이나 네트워크를 쓰지 않는다. 실제 체인에 쓰는 기능(`VITE_ENABLE_WRITES`)과 실제 거래소에 주문을 보내는 기능(`VITE_ENABLE_TRADING`)은 기본으로 꺼져 있다.

## 실행

Node 22.12 이상을 쓴다. 이 문서를 쓸 때의 환경은 22.23.1이다.

```sh
cd frontend
npm ci --ignore-scripts
npm run dev           # http://127.0.0.1:5173
npm run build         # tsc --noEmit 뒤 vite build. 빌드한 페이지에만 Content-Security-Policy가 들어간다
node --experimental-strip-types scripts/check-policy.mjs   # 빌드 뒤: dist/index.html의 정책 확인
npm test              # src/**/*.test.ts (node:test)
npm run format        # prettier --write
npm run format:check
npm run abi           # 저장소 루트에서 forge build를 한 뒤 src/abi/*.json을 다시 만든다
```

`npm run abi`는 `../out`의 forge 산출물에서 ABI를 꺼낸다. 생성된 `src/abi/*.json`은 소스와 함께 둔다. `node scripts/export-abi.mjs --check`는 그 파일이 산출물과 같은지 확인한다.

## 환경 변수

`.env.example`을 `.env.local`로 복사해 채운다. `VITE_`로 시작하는 값은 브라우저에 그대로 공개되므로 비밀키나 API 비밀을 넣지 않는다.

| 변수 | 기본값 | 뜻 |
| --- | --- | --- |
| `VITE_CHAIN_ID` | `999` | `999`(HyperEVM), `998`(HyperEVM Testnet), `31337`(로컬 Anvil) 중 하나. 숫자만 쓴다. 앞뒤 공백이나 `0x3e7` 같은 표기, 다른 값이면 빌드가 실패하고 화면이 시작하지 않는다 |
| `VITE_RPC_URL` | 체인별 공개 RPC | 계약 조회에 쓰는 EVM RPC. 비워 두면 999·998은 Hyperliquid 공개 RPC, 31337은 `http://127.0.0.1:8545`. 공개 RPC는 IP당 분당 100건만 받는다(아래 "조회 주기와 요청 수") |
| `VITE_FACTORY_ADDRESS` | 없음 | 이 빌드가 쓰는 `ManagedUsdcVaultFactory` 주소. 정해 두면 화면에서 바꿀 수 없다. 비워 두면 방문자가 주소를 입력하고, 모든 화면에 "직접 입력한 Factory로 동작합니다"라는 경고가 붙는다. 주소가 아닌 값을 넣으면 계약을 조회하지 않고 설정 오류를 알린다 |
| `VITE_VAULT_ADDRESS` | 없음 | 계약 연결 모드의 볼트 탐색에서 "주소로 열기" 칸에 미리 채울 Vault 주소 |
| `VITE_ENABLE_WRITES` | `false` | `true`일 때만 지갑으로 체인에 거래를 보낸다. 그 밖의 값이면 읽기 전용이다 |
| `VITE_CHAT_URL` | 없음 | 대화 서버(`../server`)의 절대 URL. 서버의 `CHAT_AUDIENCE`와 같아야 한다. 비우면 대화 탭이 "설정되지 않았다"고 알린다 |
| `VITE_ENABLE_TRADING` | `false` | `true`일 때만 브라우저의 서명 키로 서명한 주문을 Hyperliquid 거래소에 보낸다. 그 밖의 값이면 서명하지 않은 미리보기만 보여 준다 |
| `VITE_BUILDER_FEE_TENTHS_BPS` | `0` | 주문마다 붙일 builder fee. 단위는 0.1bp다. Vault가 Core에 승인한 값보다 크게 붙지 않는다 |

## 화면

| 주소 | 화면 |
| --- | --- |
| `#/` | 볼트 탐색 |
| `#/create` | 볼트 만들기 |
| `#/vault/<주소>` | 볼트 상세의 입금 탭 |
| `#/vault/<주소>/<탭>` | 탭은 `withdraw`, `chat`, `manage`, `trade`, `scope` |

### 볼트 탐색

Factory가 만든 볼트를 최신순으로 6개씩 보여 주고 "더 보기"로 이어 읽는다. 6개인 이유는 요청 수다(아래 "조회 주기와 요청 수"). 카드에는 이름, Factory에서의 번호(`#N`)와 주소 전체, 운용자, 단계, NAV, 지분 1개당 가치, 성과수수료, 최소 입금이 나온다. 이름은 운용자가 정하므로 두 볼트의 이름이 같을 수 있다. 볼트를 구별하는 것은 번호와 주소다. 연결한 계정이 운용자인 볼트에는 "내 볼트" 표시가 붙는다. 입금이 닫혀 있으면 그 사실과 이유를 함께 보여 준다. 이유는 Vault의 `totalAssets`가 되돌린 계약 오류에서 온다.

Vault는 운용자가 코드를 바꿀 수 있는 프록시다. 생성 때와 다른 코드로 동작하는 볼트의 카드에는 "코드 변경됨" 표시가, 업그레이드가 제안된 볼트의 카드에는 "업그레이드 제안됨" 표시가 붙는다. 답하지 않거나 이해할 수 없는 값을 답하는 볼트는 "읽을 수 없는 볼트" 카드로 주소와 이유만 보여 주고, 나머지 목록은 그대로 나온다. 그런 카드에도 controller가 기록한 "코드 변경됨"·"업그레이드 제안됨" 표시는 남는다. controller를 Vault보다 먼저, 따로 읽기 때문이다. 코드가 바뀐 볼트가 되돌린 오류와 문구는 이유로 보여 주지 않는다.

볼트가 아니라 요청이 실패한 경우(노드의 거부, 시간 초과, 요청 한도)는 다르게 다룬다. 그 줄은 "볼트 #N" 카드로 나오고, 요청이 실패한 것이며 볼트의 상태를 뜻하지 않는다고 적는다. "다시 조회"는 그 한 줄만 다시 읽는다.

Vault가 답한 이름은 96바이트까지만 화면에 쓰고 저장한다. Vault의 원래 코드는 그보다 긴 이름, 빈 이름, 제어문자가 든 이름을 받지 않으므로, 그런 이름을 답하는 볼트는 다른 코드로 보고 "코드 변경됨"으로 표시한다.

"주소로 열기"로 Vault 주소를 직접 열 수 있다. 열어 본 볼트 다섯 개는 이 브라우저의 `localStorage`에 "최근 본 볼트"로 남는다.

Factory는 볼트 목록을 주지 않는다. 화면은 Factory의 deployer nonce 규칙으로 주소를 계산하고 `isVault`로 하나씩 확인한다. RPC 조회가 실패하면 빈 목록이 아니라 오류를 보여 준다.

### 볼트 만들기

이름, 성과수수료, 최소 입금, Core 활성화 비용 상한을 입력한다. Factory의 설정을 읽은 뒤 `100 USDC + 활성화 비용`을 정확히 승인하고 `createVaultAndFund`를 보낸다. 100 USDC는 창설자 지분의 원가다. 생성이 끝나면 새 볼트의 운용 탭으로 간다. 옆에는 그 뒤의 순서(Core 활성화 확인, 평가 범위 등록, 가격 기록, 서명 키 등록, 대화)가 적혀 있다.

### 볼트 상세

위쪽에는 이름, Factory에서의 번호와 주소 전체, 단계, NAV, EVM 현금, 성과수수료, 최소 입금이 나온다. NAV를 평가할 수 없을 때는 그 아래에 "입금이 닫힌 이유"가 나온다. "내 포지션"에는 연결한 계정의 지분과 취득 원가, 볼트의 현금·출금 준비금·총 지분·운용자가 나온다.

**코드가 바뀐 볼트.** 화면은 Vault가 스스로 말하는 값 대신 Factory와, deployer가 그 Vault용으로 만든 upgrade controller에 묻는다. controller가 기록한 구현이 처음 설치된 것과 다르거나, Vault가 답하는 asset·controller 주소가 Factory의 것과 다르거나, 원래 코드가 받지 않는 이름을 답하면 "코드가 생성 때와 다릅니다"라는 경고를 크게 띄운다. 그런 볼트에서는 이름·운용자·NAV·잔액이 모두 볼트의 답일 뿐이어서 믿을 수 없다. 이 화면은 그 볼트에 입금과 새 USDC 승인을 제공하지 않고, 가격 기록도 보내지 않는다. 입금 단추만 막는 것이 아니라 입금 동작이 서명 직전에 다시 읽고 거부한다. 출금 요청과 청구는 경고와 함께 남겨 둔다. 지분을 가진 사람은 나갈 수 있어야 하기 때문이다. USDC 승인의 대상 토큰은 언제나 Factory의 asset이다.

코드가 바뀐 볼트가 조회를 되돌리거나 해석할 수 없는 값을 답해도 경고는 그대로 뜬다. 경고에 쓰는 사실(controller의 기록, 번호, 남은 승인)은 Vault에 묻지 않기 때문이다. 그 볼트가 되돌린 오류 이름과 문구는 조회에서든 출금 요청 같은 쓰기에서든 화면에 옮기지 않고, 표시하지 않는다는 문장만 보여 준다.

**남아 있는 USDC 승인.** 지갑을 연결하면 그 지갑이 이 볼트에 준 Factory asset의 승인(`allowance`)을 읽는다. 0이 아니면 탭과 관계없이 금액과 "승인 취소"(`approve(vault, 0)`)를 보여 준다. 이 화면은 입금액만큼만 승인하고 입금이 그 승인을 다 쓰므로, 남은 승인은 확정되지 않은 입금이 남긴 것이거나 다른 곳에서 준 것이다. 승인은 볼트의 코드가 바뀌어도 남고, 새 코드는 서명 없이 그만큼 가져갈 수 있다. 그래서 코드 변경 경고와 업그레이드 제안 안내도 남은 승인을 금액과 함께 적는다. 승인은 asset 계약에 묻고 asset 계약에서 취소하므로, 볼트가 답하지 않아도 보이고 취소할 수 있다. 지갑을 연결하지 않으면 읽지 않는다.

**업그레이드 제안.** controller에 제안이 올라와 있으면 언제부터 실행할 수 있는지, controller에 기록된 설치될 구현의 주소, 실행되면 코드가 바뀐다는 것을 알린다. 화면은 그 주소의 코드가 무엇을 하는지 확인하지 않는다. 제안 중에는 입금이 닫힌다.

탭은 다음과 같다. 운용·거래·평가 범위는 운용자에게만 보인다.

- **입금**: `maxDeposit`과 최소 금액을 확인하고 `previewDeposit`으로 받을 지분을 읽는다. USDC 승인을 정확히 입금액으로 맞춘 뒤 `depositWithLimit`를 보낸다. 더 큰 승인이 남아 있으면 0으로 되돌린 다음 입금액만큼 다시 승인한다. 최소 지분은 미리 본 값의 99.5%, 유효 시간은 5분이다. 승인 뒤에 입금이 확정되지 않으면(지갑에서 거절, 되돌림, 시간 초과) 승인을 다시 읽어 얼마가 남았는지 오류와 함께 알린다.
- **출금**: 지분 수량으로 `requestRedeem`을 보내고, 정산된 뒤 청구 가능한 지분 전부를 `redeem`으로 청구한다. 수령액이 0이어도 청구해서 요청을 닫을 수 있다.
- **대화**: 아래 "대화 서버 연결"을 본다.
- **운용**: 이름 변경, 다른 도구에서 만든 API wallet 주소의 등록과 해지(등록은 주소 전체와 "이 주소의 키를 가진 사람은 Core 계정의 자금 전체로 거래할 수 있다"는 문장을 보여 준 뒤 "등록 확정"을 눌러야 보낸다), USDC의 Core 왕복, lending 공급과 전액 회수, 계정 모드, 출금 정리 시작(`beginExit`), Core 결과 확인(`finalizeActivation` / `syncCoreAction`), 출금 정산(`settleEpoch`). 출금 정리 영역에는 정산 조건과 가격 기록 상태가 나온다. 화면은 증거 bytes를 만들지 않고, EVM 영수증을 Core 성공으로 보지 않는다.
- **거래**: 아래 "주문 서명 키"와 "주문"을 본다.
- **평가 범위**: 검증기가 NAV에 집계하는 토큰, perp DEX, HyperCore vault 목록을 편집해 `configure`로 통째로 저장한다. 입금 평가 스위치(`setEnabled`), 가격 기록, 범위 밖 보유 신고 목록과 "목록에서 지우기"(`clearReport`)가 있다. 목록의 순서, 중복, 상한(토큰 6, DEX 8, HyperCore vault 2)은 보내기 전에 화면에서 확인한다.

### 가격 기록

`recordPrice`는 누구나 호출할 수 있다. 그래서 "가격 기록" 단추는 운용자가 아니어도 입금 탭과 출금 탭에서 보인다. 운용자에게는 운용 탭의 출금 정리 영역과 평가 범위 탭에도 있다.

화면이 따르는 규칙은 계약 소스([검증기](../src/managed/ManagedPortfolioNavVerifier.sol), [source](../src/nav/HyperCorePrecompileSource.sol))의 것이다.

- 입금 가격을 내는 일과 출금 정산은 둘 다, 가격 창 안에 창의 절반 이상 지난 기록이 있어야 한다. 없으면 `PriceHistoryTooShort`로 거부된다. 지분이 남아 있지 않은 Vault의 출금 정산에는 기록이 필요하지 않다.
- 성립하고 있던 신고를 운용자가 그 대상을 범위에 등록해 풀면(신고에 답하면, `reportAnsweredAt`), 그때까지의 기록은 이 이력으로 세지 않는다. 그 뒤에 추가된 기록이 창의 절반만큼 지나야 한다. 이전 기록은 최고 가격의 기준으로는 계속 쓰인다. 가격 기록 영역은 세지 않는 기록의 수와 남은 시간을 보여 준다.
- 지분 가격이 창 안의 최고 기록보다 한도 넘게 낮으면 그 기록이 창을 벗어날 때까지 입금과 출금 정산이 미뤄진다(`PriceDropCooldown`).
- 새 표본은 직전 기록에서 창의 1/8보다 지난 뒤에 추가된다. 그 전에는 더 높은 가격만 직전 기록을 올린다.
- 입금 평가 스위치가 꺼져 있거나 범위 밖 보유 신고가 성립해 있어도, 관리 액션이 확인을 기다리는 동안에도 가격은 기록된다. 현금만 보유한 단계에서는 Core를 읽지 않고 현금 기준 가격을 기록한다.
- 지분이 없을 때, 현금 보유 단계가 아닌데 범위를 등록한 적이 없을 때는 기록이 거부된다. 평가 자체가 거부될 때(가격 가드, Core 순자산 음수, 조회 실패)도 그렇다.

### 범위 밖 보유 신고

평가 범위 탭은 신고 목록을 보여 주고 정리만 한다. 신고를 내는 기능은 이 화면에 없다. 신고는 Vault당 한 건만 보관된다. 성립하는 신고는 자리를 지켜서 그동안 다른 대상의 신고는 거부되고, 소멸했거나 성립하지 않는 신고는 새로 증명된 신고에 자리를 내준다. 신고는 하루 뒤 소멸한다.

신고할 수 있는 것은 등록 범위가 책임지지 않는 보유다. 등록하지 않은 토큰, perp DEX, HyperCore vault의 보유는 10 USDC 이상에 팔 수 있으면 신고할 수 있다. 등록한 토큰이라도 등록된 USDC pair가 그 보유를 주문 최소 금액(10 USDC) 이상에 사 주지 않고 차입도 없으면 신고할 수 있는데, 이때는 그 보유가 다른 pair에서 20 USDC 이상에 팔려야 한다. 등록된 DEX와 HyperCore vault, USDC는 신고할 수 없다. 그래서 목록의 신고가 등록된 토큰을 가리킬 수 있고, 화면은 그때 "등록된 pair가 이 보유를 사 주지 않음"이라고 적는다.

신고는 성립하는 동안에만 입금과 출금 정산을 닫는다. 다시 여는 길은 둘이고 결과가 다르다.

- 운용자가 그 보유를 매도하면 바로 다시 열린다.
- 성립하고 있는 신고를, 운용자가 그 대상을 범위에 등록하는 저장으로 풀면 신고는 목록에서 빠지지만 가격 이력이 새로 시작된다. 등록 뒤에 추가된 기록이 창의 절반만큼 지난 다음에 열린다. 성립하고 있는 신고의 DEX와 HyperCore vault는 등록하면 항상 그렇게 된다. 토큰은 세 경우에 그렇게 된다.
  - 등록된 USDC pair가 그 보유를 10 USDC 이상에 사 준다. 이제 종료 평가가 그 보유를 센다.
  - 그 토큰에 차입이 있다. 차입 때문에 신고된 경우가 그렇고, 등록하면 평가가 부채로 다룬다.
  - 신고에 지목된 pair에서 그 보유의 가치가 10 USDC 이상 20 USDC 미만이다. 등록하지 않은 토큰으로는 신고할 만한 크기지만 등록된 토큰으로는 못 미친다. **이 경우 그 보유는 등록 뒤 종료 평가에 잡히지도 않고 신고할 수도 없다.**

  그 밖의 경우, 곧 등록된 pair가 사 주지 않고 차입이 없으며 신고에 지목된 pair에서 20 USDC 이상에 팔리는 동안에는 등록해도 신고가 남아 Vault가 닫힌 채이며 이력도 그대로다.

이미 성립하지 않게 된 신고(대상을 먼저 비운 경우 등)나 소멸한 신고는, 그 대상을 등록하는 저장으로 목록에서 빠지기만 하고 이력은 그대로다.

평가 범위 탭은 그런 저장을 보내기 전에 결과를 알린다. 마지막 조회에서 그 신고 때문에 평가가 거부된(`OpenReport`) DEX나 HyperCore vault의 신고에는 사실로 적는다. 그렇게 보이지 않은 신고와 토큰의 신고에는 조건으로 적는다. 결과는 저장되는 블록의 호가, 보유, 차입에 달려 있고, 화면은 그것을 미리 읽어 예측하지 않는다. 토큰의 안내에는 풀리는 세 경우와 남는 경우가 모두 적혀 있다.

그래서 토큰은 매수호가가 실제로 있는 USDC pair로만 등록한다. 등록된 pair가 사 주지 않는 보유는 다른 pair에서 20 USDC 이상에 팔리면 누구나 신고할 수 있고, 매도할 때까지 입금과 출금 정산을 닫아 둔다. 20 USDC에 못 미치면 평가에도 신고에도 잡히지 않는다.

## 데모 모드

처음 화면이며 오른쪽 위의 "실제 계약 연결"로 바꾼다. 데모는 예시 볼트 일곱 개와 그 대화, 평가 범위, Core 계정을 이 브라우저의 메모리에만 둔다. 목록은 계약 연결 모드와 같이 여섯 개를 먼저 보여 주고, 일곱 번째(코드가 바뀐 "Momentum One")는 "더 보기"를 눌러야 나온다. 새로 고치거나 모드를 바꾸면 처음 상태로 돌아간다. 데모의 방문자는 예시 볼트 세 개의 운용자이고 다른 볼트 하나의 예치자다.

데모가 흉내 내는 것은 다음과 같다. 모든 동작은 "실제 거래는 전송하지 않았습니다"라고 알린다.

- 입금, 출금 요청, 청구. 현금만 보유한 볼트의 출금 요청은 바로 정산된다.
- 볼트 생성, Core 활성화 확인, 서명 키 등록과 해지, builder fee 승인.
- 평가 범위 저장과 스위치, 가격 기록, 신고 목록 정리. 신고된 대상을 등록하는 저장은 계약처럼 신고를 목록에서 빼고 가격 이력을 새로 시작한다.
- 주문. 고정된 중간가에 닿으면 체결되고 아니면 대기하며, 취소할 수 있다.
- 출금 정리 시작과 출금 정산. 정산은 계약과 같은 순서로 거부 이유를 낸다.
- 대화 참여, 글쓰기, 숨기기.

데모가 흉내 내지 않는 것도 있다. USDC의 Core 왕복, lending, 계정 모드는 안내만 표시하고 상태를 바꾸지 않는다. 그래서 운용 중인 예시 볼트는 출금 정리를 시작해도 정산까지 가지 못한다. 정산이 확정되는 흐름은 이미 회수를 마친 예시 볼트 "Genesis Exit"에서 볼 수 있다. 시장 가격은 움직이지 않는다. 계약의 가격 가드나 조회 실패는 다루지 않는다. 데모에는 호가창이 없어서, 등록된 pair가 토큰 보유를 사 주는지와 그 보유가 다른 곳에서 얼마에 팔리는지는 그 토큰의 한 시장의 고정 가격으로 따진다. 신고가 증명된 pair는 따로 두지 않는다. 예시 볼트에 걸린 신고는 perp DEX 하나뿐이다.

예시 볼트 가운데 "Momentum One"은 코드가 바뀐 볼트이고(방문자가 지분을 갖고 있다), "Stable Lending Ladder"에는 업그레이드가 제안되어 있고 예시 지갑의 USDC 승인 250 USDC가 남아 있어, 남은 승인의 안내와 "승인 취소"를 볼 수 있다. 읽을 수 없는 볼트와 조회에 실패한 줄의 예시는 없다.

## 계약 연결 모드

읽기 전용으로 시작한다.

- **Factory가 이 화면이 믿는 것의 뿌리다.** 어떤 주소가 볼트인지, 볼트가 어떤 코드로 만들어졌는지, 지갑이 승인할 토큰이 무엇인지가 모두 Factory의 답에서 나온다. 빌드가 `VITE_FACTORY_ADDRESS`를 정했으면 그 주소를 글로만 보여 주고 바꾸는 칸을 두지 않는다. 정하지 않았으면 방문자가 주소를 입력하고, 탐색·만들기·상세 화면 모두에 "직접 입력한 Factory로 동작합니다"라는 경고가 붙는다.
- 상세는 15초마다 다시 읽는다. 한 번의 조회는 모두 같은 EVM 블록의 값이다. 읽은 지 30초가 지나면 "조회 만료"로 보고, 그 값에 기대는 쓰기(입금, 출금, 운용, 평가 범위)를 막는다. RPC 조회가 실패하면 수치를 지우고 오류를 보여 준다. 조회 실패를 "평가 불가"나 0으로 바꾸지 않는다. 노드의 내부 오류도 계약의 되돌림으로 보지 않는다.
- 평가 범위와 가격 기록은 운용자의 운용·거래·평가 범위 탭에서는 20초마다, 입금·출금 탭에서는 60초마다 읽는다.
- 탭이 보이지 않는 동안에는 EVM 노드와 거래소 API를 읽지 않는다. 탭으로 돌아오면 읽을 때가 지난 것을 바로 읽는다. 열어 둔 서명 키의 자동 잠금은 탭이 보이지 않아도 진행된다.
- 지갑을 연결하지 않으면 계정별 값(지분, 취득 원가, 출금 요청, 청구 가능액, 남은 승인)을 읽지 않고 "—"로 표시한다.
- 쓰기는 `VITE_ENABLE_WRITES=true`인 빌드에서, 브라우저에 주입된 EVM 지갑으로만 한다. 서명 전에 체인과 계정을 다시 확인하고, 먼저 simulate한 뒤 보낸다. 한 번에 하나의 쓰기만 진행한다.
- 동작의 확정과 오류를 알리는 줄은 그 동작이 속한 볼트의 화면에서만 보인다. 거래가 확정되기 전에 다른 볼트로 옮겨 가면 그 화면에는 나오지 않고, 원래 볼트로 바로 돌아오면 보인다. 볼트 생성의 확정은 새 볼트의 화면에 나온다.
- 지갑의 계정이나 체인이 바뀌면 연결을 끊는다. 열어 둔 서명 키는 잠기고 대화 세션은 지워진다.
- 이 화면은 다른 사이트의 페이지 안(frame)에서는 시작하지 않는다. 그 안에서는 안내문 한 줄만 보여 주고, 지갑에 묻지도 저장된 키를 읽지도 않는다.
- 계약이 되돌리면 오류 이름과 그 뜻을 함께 보여 준다. Vault 호출 안에서 검증기나 source가 되돌린 오류도 이름으로 풀린다. 뜻은 [`src/reasons.ts`](src/reasons.ts)에 있다. 계약이 문자열로 되돌린 문구는 `계약이 되돌린 문구: "…"`로 인용해서만 보여 주고, 그 안에 오류 이름이 들어 있어도 이 화면의 설명을 붙이지 않는다. 문구에서 따옴표, 줄바꿈, 제어문자, 보이지 않는 문자와 글자 방향을 바꾸는 문자를 빼고 120자에서 자르므로, 문구가 인용을 닫거나 새 줄에서 이 화면의 말처럼 이어질 수 없다. 코드가 바뀐 볼트가 되돌린 것은 인용하지도 않는다.
- 지갑에서 요청을 거절하면 "지갑에서 요청을 거절했습니다"라고, 요청이 제시간에 응답받지 못하면 "시간 초과"라고 알린다. 지갑이 보낸 거래를 취소하거나 다른 거래로 바꾸면 그 사실을 알리고 성공으로 보지 않는다.
- 이름과 대화 글은 텍스트로만 렌더링한다. 금액과 지분은 BigInt로 다루고, 입력한 소수 자릿수를 반올림하지 않는다.

### 조회 주기와 요청 수

Hyperliquid의 공개 RPC(`rpc.hyperliquid.xyz/evm`)는 IP당 분당 100건의 JSON-RPC 요청만 받고, 이 한도는 같은 IP의 지갑과 다른 탭이 함께 쓴다. 그래서 화면은 바뀔 수 없는 값을 한 번만 읽고, 볼트를 두 부분으로 나눠 읽는다.

- **한 번만 읽는 것**: RPC의 chain ID, Factory의 `deployer`와 `templateConfig`, 볼트가 Factory에 등록되어 있다는 사실과 그 번호, 검증기의 `source`·`priceWindow`·`maxDrawdownBps`. Factory와 검증기의 이 값들은 계약 소스에서 immutable이거나 생성자에서 한 번 정해지고, 등록된 볼트는 등록이 풀리지 않는다. 검증기를 프록시 뒤에 배포해 이 값을 바꾸는 경우는 다루지 않는다(페이지를 새로 열면 다시 읽는다). 쓰기 직전에는 RPC의 chain ID를 다시 확인한다.
- **15초마다**(8건): 최신 블록, controller가 기록한 구현과 업그레이드 제안 여부, 볼트의 단계·관리 액션·총 지분·평가(`totalAssets`)·입금 한도. 입금 가능 여부를 정하는 값이다. 제안이 있으면 그 내용 2건을 더 읽는다.
- **60초마다, 그리고 동작 직후와 쓰기 직전**(지갑 연결 시 25건, 아니면 19건): 위의 값과 나머지 전부. 이름, 운용자, asset, controller, 현금, 준비금, 수수료, 최소 입금, epoch, API wallet, 활성화 비용, 계정별 값, 남은 승인. 볼트의 코드가 고정하는 값(운용자, asset, controller)도 이때마다 다시 읽어 Factory의 것과 견준다. 15초 조회에서 단계·관리 액션·총 지분·구현·제안 여부가 달라졌으면 그 자리에서 전체를 읽는다.
- **평가 범위와 가격 기록**(5건): 블록, 범위, 신고, 가격 기록, 신고에 답한 시각. 볼트의 검증기·builder 주소는 볼트의 구현이 바뀌기 전까지 처음 읽은 값을 쓴다.

모의 노드에서 탭마다 2분 동안 센 요청 수는 다음과 같다(분당, 지갑 연결). 바뀌기 전의 값은 같은 방법으로 바꾸기 전 빌드를 센 것이다.

| 화면 | 전 | 후 |
| --- | --- | --- |
| 입금·출금 탭 | 171 | 54 |
| 입금 탭, 지갑 연결 없음 | 171 | 48 |
| 대화 탭 | 160 | 49 |
| 운용·거래·평가 범위 탭 | 215 | 64 |
| 볼트 탐색(열어 둔 상태) | 0 | 0 |
| 볼트 탐색의 첫 쪽을 한 번 읽을 때 | 129건(10개) | 67건(6개) |

볼트 탐색은 열어 둔 동안 다시 읽지 않는다. 다만 한 줄을 읽는 데 약 10건이 든다(등록 확인 1, controller 2, 볼트 7. 입금이 닫힌 볼트는 2건 더). 10개씩 읽으면 한 번에 109건으로, 방문자가 아무것도 열기 전에 공개 RPC의 분당 한도를 넘는다. 그래서 한 쪽을 6개로 두었다. 모의 노드의 6개는 67건이었고, 닫힌 볼트가 없으면 64건이다.

이 예산에는 여유가 크지 않다. 볼트 하나를 처음 여는 데 30~40건이 들고 그 뒤로 위 표의 조회가 이어지므로, 목록을 연 같은 1분 안에 "더 보기"를 누르거나 볼트를 열면 그 1분의 요청이 한도를 넘을 수 있다. 그때는 일부 줄이 "다시 조회" 카드로 나오거나 상세가 잠시 조회 오류를 보인다. 상세는 다음 조회에서 돌아오고, 목록의 줄은 "다시 조회"를 눌러 다시 읽는다. 자체 RPC를 쓰는 배포(`VITE_RPC_URL`)는 이 한도에 묶이지 않으므로 [`src/pages/Explore.tsx`](src/pages/Explore.tsx)의 `PAGE`를 올려 한 쪽에 더 많이 보여 줘도 된다. multicall과 JSON-RPC 일괄 요청은 쓰지 않는다. 한 볼트가 전체 호출의 가스를 다 써서 목록 전체를 실패시킬 수 있고, 일괄 요청이 한도에 어떻게 계산되는지 확인하지 못했다.

## 주문 서명 키

HyperCore의 주문은 chain ID 1337로 고정된 형식의 서명이 필요해서 브라우저 지갑으로는 서명할 수 없다. 그래서 거래 탭은 Vault 전용 **서명 키(agent key)**를 이 브라우저에서 만든다. 이 키는 Vault의 Core 계정으로 거래할 수 있지만 출금할 수는 없다.

**만들기와 등록**

1. 암호를 두 번 입력한다. 12자 이상이어야 한다.
2. 브라우저가 새 개인키를 만든다.
3. 그 키를 암호로 암호화해 `localStorage`의 `corevault:agent:<chain ID>:<Vault 주소>`에 저장한다.
4. 지갑으로 `setApiWallet(키의 주소)`를 보낸다. Vault에 확인을 기다리는 관리 액션이 생긴다.
5. 다음 Core 블록부터 "Core 반영 확인"(`syncCoreAction`)으로 확정한다. 그 전에 누르면 `ActionNotFinal`로 거부된다.
6. Vault의 `apiWallet`이 저장된 키의 주소와 같고, 거래소 API가 그 주소를 활성 agent로 표시하면 "사용 가능"이 된다.

**암호화**

암호에서 PBKDF2-SHA-256(600,000회, 임의의 16바이트 salt)으로 키를 얻고 AES-256-GCM(임의의 12바이트 IV)으로 개인키를 암호화한다. 저장되는 것은 주소, salt, IV, 암호문, 반복 횟수, 만든 시각이다. 평문 개인키와 암호는 저장하지 않는다. 저장된 기록을 읽을 때는 형식, salt·IV·암호문의 길이(16·12·48바이트), 반복 횟수(600,000~6,000,000)를 확인하고, 복호한 키의 주소가 기록의 주소와 같은지 확인한다. 이 확인을 통과하지 못한 기록은 "손상된 기록"으로 알린다. 암호를 묻지 않고(어떤 암호로도 열 수 없으므로 "암호가 틀렸다"고 하지 않는다), 방문자가 "손상된 기록 지우기"를 누르기 전에는 지우지도 덮어쓰지도 않는다.

**쓰기**

"잠금 해제"에 암호를 넣으면 키가 이 탭의 메모리에만 올라온다. "잠금"을 누르거나, 거래 탭을 벗어나거나, 지갑 계정이 바뀌면 다시 잠긴다. 거래 동작이 10분 동안 없어도 잠긴다. 거래 동작은 잠금 해제, 시장 선택, 주문 입력과 확인, 전송, 취소다. 남은 시간은 키 영역에 표시된다. 탭이 뒤에 있어 잠금 타이머가 늦게 돌더라도, 전송할 때 시간을 다시 확인하므로 10분이 지난 키로는 서명하지 않는다. 개인키와 암호는 화면에 표시하지 않고, 로그나 주소나 오류 문구에 넣지 않고, 클립보드로 복사하지 않는다.

암호화된 기록은 이 브라우저 밖으로 복사해 계속 추측해 볼 수 있다. 그래서 암호가 키의 유일한 보호이며, 길이 12자는 이 화면이 확인할 수 있는 최소한일 뿐이다.

**Vault를 조회하지 못할 때**

주문은 이 브라우저의 키로 서명해 거래소로 보내므로 EVM 조회가 없어도 된다. 페이지를 새로 연 뒤 EVM 조회가 실패하고 있어도, 이 브라우저에 그 Vault의 키가 있으면 거래 탭을 그린다. 키의 상태는 거래소 API가 그 주소를 활성 agent로 표시하는지로 정하고, 미체결 주문 취소와 reduce-only 주문을 보낼 수 있다. 키 만들기·등록·해지, Core 반영 확인, builder fee 승인처럼 Vault와 지갑이 필요한 기능은 조회가 돌아온 뒤에 쓴다.

**잃었을 때**

키나 암호를 잃으면 되찾을 수 없다. "키 폐기"로 이 브라우저의 기록을 지우고, 등록을 해지한 뒤 새 키를 만든다. 한 번 등록에 쓴 주소는 다시 등록할 수 없다. 다른 브라우저나 기기에서는 그 기기에서 새 키를 만들어 등록한다.

### 주문

- **시장**: 공개 API에서 시장 목록을 읽는다. 포지션을 열거나 늘릴 수 있는 주문은 평가 범위에 등록된 시장에만, 범위를 최근(30초 안)에 읽었을 때만 보낼 수 있다. USDC로 호가되지 않는 spot pair와 USDC 담보가 아닌 DEX는 지원하지 않는다. 검증기에 평가 범위가 없는 Vault에서는 나머지 시장을 모두 고를 수 있고, 범위를 이 화면에서 확인할 수 없다는 경고가 나온다. 이것은 검증기가 정말로 범위를 갖지 않을 때만이다.
- **범위가 막지 않는 것**: 미체결 주문 취소와 perp의 reduce-only 주문은 키만 열려 있으면 보낼 수 있다. 둘 다 포지션을 열거나 늘릴 수 없기 때문이다. 범위 밖 perp 시장, 범위 조회가 만료되었거나 실패한 때, 범위를 아직 읽지 못한 때에도 USDC perp 시장은 "reduce-only 주문만"이라는 표시와 함께 고를 수 있고, 그렇게 고르면 주문은 reduce-only로 시작한다. spot에는 reduce-only가 없으므로 spot 주문은 범위를 기다린다. 계정과 미체결 주문 목록은 범위를 읽지 못해도 모든 DEX를 읽어 보여 준다.
- **주문 유형**: 지정가(Gtc), 지정가 Post-only(Alo), 즉시 체결(중간가에서 슬리피지만큼 불리한 가격의 Ioc. 슬리피지는 0.01~10%, 기본 1%). perp에는 reduce-only가 있다.
- **확인**: 가격은 유효숫자 5자리와 시장별 소수 자릿수, 수량은 시장별 소수 자릿수, 주문 금액은 10 USDC 이상인지 확인한다. 한 줄 요약을 "주문 확인" 단추 위에 보여 주고 "주문 전송"을 한 번 더 눌러야 한다. 요약은 30초 동안만 유효하고, 30초가 지난 요약은 화면에서 사라질 뿐 아니라 눌러도 전송하지 않는다. 확인을 기다리는 동안(현재가를 읽는 동안) 주문을 고치거나 다른 시장을 고르면 늦게 돌아온 확인은 버린다.
- **두 번 누름**: 요약이 뜬 뒤 0.7초 안의 누름은 "주문 전송"과 동의 체크 모두에서 무시한다. "주문 확인"을 두 번 빠르게 누른 두 번째 누름이 전송이 되지 않게 하기 위해서다. 배치도 같은 목적이다. "주문 확인" 단추는 제자리에 남아 비활성이 되고, 요약 상자는 그 위에 글이 먼저, 단추가 나중에 오게 놓인다. 검토의 오류 문구는 단추 아래에 나온다.
- **현재가에서 먼 지정가**: 지정가(Gtc)가 현재가(mid)보다 1% 넘게 불리한 쪽에 있으면(매수가 더 높거나 매도가 더 낮으면) 대기하지 않고 바로 그 가격까지 체결될 수 있다. 이때는 그 차이를 %로 적은 문장에 따로 동의해야 전송할 수 있다. 현재가를 읽지 못했을 때도 같은 동의를 받는다. Post-only는 거래소가 체결 대신 거부하고, 즉시 체결은 슬리피지를 직접 입력하므로 묻지 않는다.
- **전송**: nonce는 밀리초 시각이며 쓰기 전에 `localStorage`에 적어 두어 다시 쓰지 않는다. 서명한 요청은 60초 뒤 만료된다. 거래소가 20초 안에 답하지 않으면 기다리기를 멈춘다. `VITE_ENABLE_TRADING`이 `true`가 아니면 서명도 전송도 하지 않고 보낼 내용을 "전송하지 않은 미리보기"로 보여 준다.
- **결과**: 접수·대기, 체결, 거부를 주문별로 보여 준다. 요청이 나간 뒤 오류가 나거나 시간이 초과되면 "결과를 알 수 없다"고 알리고 다시 보내지 않는다. 미체결 주문을 확인한 뒤 직접 다시 시도해야 한다.
- **builder fee**: Vault에 builder가 있고 Core에 승인된 값이 0보다 클 때만 붙인다. 붙는 값은 `VITE_BUILDER_FEE_TENTHS_BPS`와 승인된 값 중 작은 쪽이다. "builder fee 승인"은 `approveBuilderFee`를 보내고 Core 반영 확인을 거친다.
- **계정**: 거래소 HTTP API가 보여 주는 DEX별 계정 가치, 포지션, spot 잔액, 미체결 주문이다. 10초마다(등록 DEX가 많으면 더 드물게) 다시 읽는다. 온체인 NAV가 아니며 지분 가격에 쓰이지 않는다. 범위에 없는 보유에는 "범위 밖" 표시가 붙는다. 조건부 주문은 유형과 조건가를 보여 주고, 수량이 0이면 "포지션 전체"로 표시한다.

## 대화 서버 연결

대화는 별도 서버([`../server`](../server/README.ko.md))가 맡는다. `VITE_CHAT_URL`에 그 서버의 절대 URL을 넣는다. 이 값은 서버의 `CHAT_AUDIENCE`와 글자 그대로 같아야 한다(끝의 `/` 제외). 다르면 참여 서명이 거부된다.

- 글은 누구나 읽을 수 있다. 화면은 5초마다 새 글을 읽고, 30초마다 최근 글을 다시 읽어 숨김 상태를 맞춘다. 탭이 보이지 않을 때는 읽지 않는다.
- 글을 쓰려면 "지갑 서명으로 참여"를 누른다. 지갑은 EIP-712 서명 하나를 만든다. 거래를 보내지 않고 가스가 들지 않는다. 서버가 준 세션은 이 탭의 `sessionStorage`에 두고, 만료되거나 지갑 계정이 바뀌면 버린다.
- 그 볼트의 운용자와 예치자만 글을 쓸 수 있다. 역할은 서버가 체인을 읽어 정한다. 운용자는 글을 숨기거나 다시 보이게 할 수 있다.
- 글은 1,000자까지이고 줄바꿈 외의 제어문자를 쓸 수 없다.
- 대화는 공개 기록이다. 글은 각 작성자의 의견이며 플랫폼의 투자 조언이 아니다. 화면에도 그렇게 적혀 있다.

## 배포할 때: Content-Security-Policy

이 화면은 거래 키를 다루므로, `npm run build`가 만든 `dist/index.html`에는 Content-Security-Policy가 meta 태그로 들어간다. 개발 서버는 자체 inline 스크립트를 쓰므로 넣지 않는다. 정책은 빌드할 때의 환경 변수에서 만든다([`src/csp.ts`](src/csp.ts)).

| 지시문 | 값 | 뜻 |
| --- | --- | --- |
| `default-src` | `'self'` | 따로 정하지 않은 것은 이 사이트의 것만 |
| `script-src` | `'self'` | inline 스크립트와 `eval`은 실행되지 않는다 |
| `connect-src` | RPC, Hyperliquid API, 대화 서버의 origin | `VITE_RPC_URL`(없으면 체인의 공개 RPC), `VITE_CHAIN_ID`에 맞는 Hyperliquid API, `VITE_CHAT_URL`. 로컬 체인(31337)에는 API가 없고, `VITE_CHAT_URL`이 비어 있으면 대화 서버도 빠진다 |
| `style-src`, `font-src` | `'self'` | 스타일과 글꼴도 이 사이트의 것만. inline `<style>`은 적용되지 않는다 |
| `object-src`, `base-uri`, `form-action` | `'none'` | |

- **제3자에게서 받는 것이 없다.** 글꼴은 방문자 시스템의 것을 쓴다(`src/style.css`: system-ui, Apple SD Gothic Neo, Malgun Gothic, 설치되어 있으면 Noto Sans KR). 그래서 글자 모양은 운영체제마다 다르다. 스크립트·스타일·글꼴·이미지를 다른 origin에서 불러오는 코드를 넣으면 빌드한 페이지에서는 막힌다.
- 환경 변수가 정책에 넣을 수 없는 값이면 빌드가 실패한다. 지원하지 않거나 숫자만으로 쓰지 않은 chain ID, 절대 URL이 아니거나 http(s)가 아닌 `VITE_RPC_URL`·`VITE_CHAT_URL`, 사용자 이름·비밀번호가 든 URL, 그리고 host에 `*`나 `;`처럼 호스트 이름에 쓸 수 없는 문자가 든 URL이 그렇다. 정책에서 `*`는 모든 host를 뜻하고 `;`는 지시문을 끝내기 때문이다.
- 정책에 쓰는 값은 빌드가 실제로 쓴 값이다. Vite가 설정의 env 디렉터리에서 읽어 페이지에 넣는 바로 그 값이며, 명령을 실행한 디렉터리와는 관계없다.
- `node --experimental-strip-types scripts/check-policy.mjs`는 빌드 뒤에 `dist/index.html`을 확인한다. 정책 meta 태그가 head의 첫 요소이고, 내용이 지금의 환경 변수로 만든 정책과 글자 그대로 같고, 정책이 하나뿐이어야 통과한다. 저장소의 `scripts/test_frontend.sh`가 빌드 다음에 이 확인을 돌린다.
- **`frame-ancestors`는 meta 태그로 정할 수 없다.** 이 화면이 다른 사이트의 frame 안에 뜨지 않게 하려면 호스트가 응답 헤더로 `Content-Security-Policy: frame-ancestors 'none'`을 보내야 한다. 이 저장소는 호스트 설정을 제공하지 않는다. 호스트에 기대지 않는 대비로, 화면은 다른 origin의 frame 안에 있으면 시작하지 않는다([`src/frame.ts`](src/frame.ts)). 이것은 스크립트가 실행된 뒤의 판단이므로 헤더를 대신하지 못한다.
- 빌드한 뒤 환경 변수를 바꿔도 정책은 바뀌지 않는다. RPC나 대화 서버의 주소를 바꾸면 다시 빌드한다.

## 한계와 확인 범위

**이 화면으로 실제 체인에 거래를 보내거나 실제 거래소에 주문을 낸 적이 없다.** 실제 지갑으로 서명해 본 적도 없다. 쓰기와 주문 전송은 기본으로 꺼져 있고, 저장소는 실자금용 설정이나 배포 주소를 제공하지 않는다.

확인한 것은 다음뿐이다.

- `npm run format:check`, `npm run build`, `npm test`. 단위 테스트는 금액과 이름의 검증, 주소 해석, 평가 범위 편집과 `configure` 인자, 가격 기록 규칙, 주문 만들기와 검증, 서명 키 상태 판단, 대화 목록 병합, 오류 풀이, 데모 모형을 다룬다. 테스트 수는 [STATUS](../docs/STATUS.ko.md)에서 관리한다.
- 데모 모드를 headless Chrome에서 1280px와 390px 너비로 열어 각 화면과 주요 동작을 눌러 보았다.
- 계약 연결 모드는 저장소에 없는 임시 도구로만 돌려 보았다. 메모리 안의 모의 JSON-RPC, 모의 지갑, 브라우저 안에서 가로챈 Hyperliquid API 응답, 로컬 대화 서버를 썼다. 화면이 보내는 calldata와 주문 본문, 서명자를 확인한 것이며 네트워크 증거가 아니다. 그 모의 체인의 규칙은 계약 소스를 읽고 손으로 옮긴 것이다.
- 같은 임시 도구를 빌드한 페이지에도 돌려, 그 흐름에서 Content-Security-Policy 위반이 나지 않는 것을 보았다. 빌드한 페이지에서 허용하지 않은 origin으로의 요청, inline 스크립트와 스타일, `eval`, 다른 origin의 스타일시트·글꼴·이미지가 막히는 것도 headless Chrome에서 확인했다. 지갑 확장 프로그램이 있는 실제 브라우저에서는 확인하지 않았다.
- 글꼴은 macOS의 Chrome에서만 보았다. Windows, Android, Linux에서 시스템 글꼴로 어떻게 보이는지는 확인하지 않았다.

남은 한계는 다음과 같다.

- 지갑 선택 모달과 WalletConnect가 없다. 브라우저에 주입된 지갑 하나만 쓴다.
- 코드가 바뀐 볼트는 controller가 기록한 구현으로 알아낸다. 업그레이드했다가 처음 구현으로 되돌린 볼트는 바뀌지 않은 것으로 읽힌다. 코드가 바뀐 볼트의 운용자 탭은 막지 않고 경고만 한다.
- 서명 키의 자동 잠금은 이 탭의 타이머와 전송 시점의 확인에 기댄다. 탭이 뒤에 있으면 메모리의 키가 지워지는 시점은 10분보다 늦을 수 있다.
- 볼트 목록은 indexer 없이 RPC로 하나씩 읽는다. 상세 화면의 요청은 공개 RPC의 분당 한도 아래로 줄였지만("조회 주기와 요청 수"), 목록 한 쪽(6개)을 읽는 데 60건 남짓이 들어 목록을 연 직후에 볼트를 열면 그 1분의 요청이 한도에 닿을 수 있다. 실제 공개 RPC에서 한도에 걸리는지, 걸렸을 때 노드가 어떤 오류로 답하는지는 확인하지 않았다.
- 요청 수는 모의 노드에서 센 것이다. 지갑 확장 프로그램이 같은 RPC로 보내는 요청은 포함하지 않는다.
- "주문 확인"을 두 번 누르는 경우는 headless Chrome에서 1440·1280·390px 너비로만 눌러 보았다. 브라우저가 화면을 붙잡아 두는 방식(scroll anchoring)은 브라우저마다 다르므로, 배치만으로 모든 브라우저에서 같다고 보지 않는다. 0.7초 규칙이 배치와 무관한 쪽의 보장이다.
- NAV 수익률 시계열, 업그레이드 제안·실행 화면, 도착하지 않은 회수의 포기(`abandonRecall`) 화면, 범위 밖 보유를 신고하는 화면이 없다.
- 출금 정산은 계약에서는 누구나 호출할 수 있지만 이 화면은 운용 탭에서만 제공한다.
- 볼트 상세는 입금이 닫힌 볼트의 NAV를 표시하지 않는다. 볼트 탐색의 카드는 검증기의 조회용 값(`nav`)이 있으면 그것을 보여 준다.
- 운용 탭의 lending 수량은 그 토큰의 Core 원시 단위다. EVM USDC의 소수 금액과 다르다.
- 서명 키는 이 브라우저에만 있다. 같은 출처에서 실행되는 스크립트는 `localStorage`의 암호문을 읽을 수 있으므로, 암호의 강도가 곧 키의 보호 수준이다.

## 자산별 Vault 화면 (2026-10-11)

`#/assets`는 새 `ManagedAssetVaultFactory`용 별도 화면이다. `VITE_ASSET_FACTORY_ADDRESS`를 지정하면 해당 주소로 고정하며, 기존 `VITE_FACTORY_ADDRESS` 설정과 구분한다. 미설정이면 검토한 새 Factory 주소를 직접 입력할 수 있다. 로컬에 실제 Factory를 배포한 것은 아니며 쓰기/주문 기본 off를 유지한다.

USDC/HYPE/UBTC 선택·생성, 자산 단위 입금, 전액 출금 요청·청구, 배정 예약/실행·회수·동기화·agent·정산, 기본 평가 범위와 가격 기록을 제공한다. HYPE는 Factory가 만든 native Router를 사용한다. 기본 scope는 USDC+기준 자산+DEX 0이며 다른 시장·token 범위 설정은 별도다. 새 Vault를 기존 USDC 주문·채팅 페이지에 넣지 않는다. 소수점 초과 입력을 반올림하지 않고 거부한다.

Factory가 기록한 자산·upgrade controller·첫 구현·native Router로 신규 입금의 대상을 확인한다. 구현이 바뀌면 입금을 차단하고 직접 token 청구를 유지한다. HYPE native claim에 쓴 operator 승인은 청구 후 해제하며, 실패로 승인이 남으면 승인 취소 버튼을 사용할 수 있다. [계약·운용 명세](../docs/managed-asset-vault.ko.md).
